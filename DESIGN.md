# swarmboard design (draft)

*Working name. Status: draft for discussion; nothing here is built yet.*

swarmboard is forum software for I2P where one operator runs the site and its members mirror it.
Text travels only over I2P. Images and video travel over I2P or clearnet BitTorrent, board by
board, as the operator chooses. Old pages are frozen, hashed and signed, so any mirror can serve
them and a link to an old post keeps working even when the operator's server is down.

## Goals

- **Resilience:** a site's history survives its server going offline, because members hold
  verified copies.
- **Privacy in layers:** the text layer is I2P only. Media can trade privacy for bandwidth, but
  only on boards the operator marks that way, and a user's client can always be stricter.
- **Accountable moderation:** one operator, moderators the operator appoints, and revocation that
  every honest client applies.
- **Spam resistance once LLMs make text cheap:** posting costs something a bot farm can't fake
  cheaply, and part of that cost goes into hosting the site.
- **Off-the-shelf parts:** i2pd, BitTorrent, ed25519 and existing formats wherever they fit.
- **An open protocol:** a dedicated client comes first. Other clients, rynx among them, can read
  sites without it.

## Non-goals

- Multi-writer or serverless forums. The operator's server is the only writer, and mirrors only
  copy what it signed.
- Censorship that nobody can undo. Revocation is deliberately part of the design (see
  [Moderation](#moderation-and-revocation)).
- Anonymity on the clearnet tier. That tier gives faster media, not privacy.
- Real-time chat.

## Roles

| Role | What it does |
|---|---|
| **Operator** | Owns the site's root key, runs the server (the only writer), seals epochs, appoints moderators |
| **Moderator** | Holds a key the operator certified, with a scope (boards) and an expiry. Can hide, revoke and ban within that scope |
| **Member** | Has a key, can post, and must seed a quota (see [Seeding](#the-seeding-obligation)) |
| **Reader** | Reads without a key, seeds nothing, can't post |
| **Mirror** | Any node holding sealed epochs: members' clients, a member's home node (such as a Raspberry Pi), volunteers |
| **Seedbox** | A clearnet BitTorrent seeder run by the operator or trusted volunteers. It seeds new clearnet-tier media first, so posters never have to (see [Leaks](#leaks-and-how-the-design-closes-them)) |

## Keys and identity

Every signature is ed25519.

- **Root key:** the operator's identity. It should be kept offline, and it only signs site keys
  and moderator certificates.
- **Site key:** signs manifests, sealed epochs and revocation lists, and lives on the server.
  If it is compromised, the root key signs a replacement and revokes the old one.
- **Moderator certificate:** `{moderator key, boards, powers, expires}`, signed by the root key.
- **Member key:** generated by the client. Every post is signed by its author's member key, and
  the server countersigns the post when it accepts it.
- **Node certificate:** a member key may vouch for a node key (`{node key, expires}`). Seeding
  that node does then counts toward the member's quota, so someone on a phone or on the glasses
  can seed from home.

The site's address is its I2P destination. The root key's fingerprint is its permanent
identity: clients pin it on first visit, like SSH host keys. A manifest signed by any other root
key is a different site.

## Content model

```
site
└── board (tier, rules)
    └── epoch 0, 1, 2 …   (append-only log of posts; threads are reply chains within it)
        └── post (author key, server countersignature, text, media references)
```

### Epochs

Each board's posts form one append-only log, cut into **epochs**. An epoch closes after N posts
or T time, whichever comes first (defaults suggested: 500 posts or 7 days).

An epoch passes through three states:

1. **Open:** new posts arrive. Only the server holds it, and clients fetch it from the server.
2. **Settling:** closed to new posts, but moderators can still remove posts. This is the
   moderation window (suggested: 72 hours). Sealing spam immediately would mirror it forever.
3. **Sealed:** serialised deterministically, compressed, hashed and signed. The epoch is then
   immutable, and any mirror can serve it.

A sealed epoch carries the hash of the board's previous sealed epoch. Each board's history is
therefore a hash chain, so a mirror can't drop or reorder epochs without being noticed.

Threads cross epochs: a reply in epoch 9 can point to its parent in epoch 3. Epochs are a
storage unit, not a page of the forum. The client builds thread views from whatever epochs it
holds and fetches any it's missing.

### Links

```
sb://<root-fingerprint>/<board>/<epoch>/<post-number>
```

A link to a sealed epoch resolves from any mirror and is checked against the hash chain. A link
into an open epoch resolves only from the server until that epoch seals.

### The manifest

The manifest is the site's signed, current head. It is small and fetched often:

```
{
  site: root fingerprint, site-key certificate,
  sequence: 1042,                       // monotonically increasing; highest valid wins
  boards: [{ name, tier, rules-hash,
             sealed: [ { epoch, sha256, size, infohash } … ],
             open: epoch number }],
  revocations: { sequence, sha256 },    // see Moderation
  moderators: [ certificates ],
  published: timestamp,
}
```

Because the manifest is signed, a mirror can relay it. A client accepts the highest sequence
number it has seen that carries a valid signature, so a stale mirror can delay updates but can't
roll a client back. BitTorrent's BEP 46 (a mutable item in the DHT, keyed by an ed25519 key) is
a candidate way to publish the manifest when the server is offline.

### Bundle format

A sealed epoch is a deterministic archive, so every honest sealer produces identical bytes:

- post records in CBOR, sorted by post number;
- on boards of tier 1 or higher, the thumbnails of the epoch's media;
- compressed with zstd at a fixed level.

Media are not stored in the bundle. Posts refer to them as
`{sha256, size, mime, tier, infohash?}`. Every file's SHA-256 is listed whether or not BitTorrent
v2 is used, so any copy from any source can be verified.

## Tiers

The operator sets a tier for each board. A client may treat a board as a lower tier (more
private), but never as a higher one.

| Tier | Text | Media | Typical use |
|---|---|---|---|
| **0** | I2P | none (links only) | discussion, sensitive boards |
| **1** | I2P | images re-encoded small (suggested cap: 500 KB), fetched over I2P | most boards |
| **2** | I2P | full-size media over clearnet BitTorrent | cat videos, public art, large files |

A client in **locked I2P mode** treats every board as tier 1 at most and never opens a clearnet
socket. Each tier 2 board shows a plain notice when first visited: the fetches are public, and
seeders may receive copyright complaints.

## Distribution

- **The server** serves the manifest, open epochs and uploads over I2P, using plain HTTP inside
  I2P (the simplest thing an I2P client can use).
- **Sealed epochs** are shared as torrents within I2P (via SAM, in I2PSnark's network) and can
  also be fetched from the server.
- **Tier 1 media** are shared as I2P torrents, one torrent per epoch. Fetching a whole epoch's
  images at once reveals only "this peer reads this board", not which post it opened.
- **Tier 2 media** are shared as clearnet torrents, also one per epoch, fetched after a random
  delay (see [Leaks](#leaks-and-how-the-design-closes-them)).
- **Mirrors** announce what they hold through the I2P DHT and trackers. No index of who mirrors
  what is kept centrally.

## Posting media

1. The client strips metadata (EXIF, GPS, camera serials) and re-encodes the file, at the tier
   1 size if the board is tier 1.
2. It uploads the file to the server over I2P with the post.
3. The server strips and re-encodes again (never trust the client), then checks the file against
   perceptual-hash blocklists. On tier 1 image boards, new members' uploads go to a moderator
   for approval first.
4. When the post is accepted, the operator's seedboxes (for tier 2) or the server (for tier 1)
   start seeding.
5. The poster's client **never seeds its own fresh upload on the clearnet**. On tier 2 it may
   start seeding once the epoch seals and the swarm already has other seeders, or never.

## The seeding obligation

Posting requires seeding. This makes members host the site, and makes spam cost bandwidth.

- **Quota:** a member must seed at least Q (operator's choice; suggested: 2 GB, or 5% of the
  site's sealed data, whichever is less) of eligible content.
- **Eligible content:** sealed epochs and media the operator approved and has not revoked, and
  **not the member's own posts**. Within that, members choose what they seed.
- **Proof, not self-reporting:** at random times the server asks a member's node, over I2P, for
  a random 16 KB range of a file it claims to hold, and checks the range against the file's hash
  tree. Ratios that clients report themselves, as on private trackers, are trivially faked.
- **Low-bandwidth members:** a node certificate lets a home node (a Pi, a desktop) seed for a
  member on a phone or glasses. The operator may also give a small posting allowance to members
  with no seeding, for example 3 posts a day.
- **Side effect:** a spam farm that meets the quota ends up hosting the site. The quota alone is
  cheap for a VPS, so it is combined with the measures in
  [Spam](#spam-in-the-llm-era).

## Moderation and revocation

- **The revocation list** is append-only and signed by the site key. Moderators' entries are
  countersigned by the server. Each entry is `{target, kind, scope, reason code, moderator,
  time}`, where the target is a post, a file hash, a member key or a whole epoch.
- **Clients honour revocations by default.** They hide the post, stop seeding the file and
  delete it from disk. Any client can technically ignore the list, so the design limits the harm
  of ignoring it:
  - revoked content no longer counts toward seeding quotas;
  - official clients won't fetch revoked hashes from any source;
  - mirrors that keep serving revoked hashes can be listed and avoided.
- **Kinds of revocation:**
  - *hide:* rule breaking or spam. The post stays in the sealed epoch, and honest clients hide
    it.
  - *purge:* illegal content. Honest clients delete the bytes, and the server deletes them from
    its own copy. A sealed epoch can't be changed, so the hash of the purged item goes on the
    list and clients store the epoch with that item removed.
- **Bans** are revocations of member keys, with scope (a board or the whole site) and an expiry.
  A banned key's later posts are refused, and its earlier ones can be hidden in bulk.
- **Shared hash blocklists:** a site can subscribe to blocklists other operators sign, and
  combine them with its own.

## Spam in the LLM era

Content filters stop working once spam reads like a person wrote it. The design relies on cost
and accountability instead:

- **Proof of work per post:** cheap for one person, costly in bulk (ALTCHA-style SHA-256
  puzzles, difficulty set per board).
- **Identities that earn rights over time:** a new key gets low rate limits, and can't post
  media or links until it is some days old and has some accepted posts.
- **Invite trees (optional per site):** a new member needs an invite from an existing member.
  Banning a member flags whoever invited them, and moderators can ban a whole branch.
- **Seeding quota** (above).
- **Rate limits on reports and tags,** weighted by the reporter's standing, so generated reports
  can't bury the moderators.
- **Hand appointment of moderators only:** no reputation score or vote ever grants moderator
  powers. Patient sockpuppets that farm reputation for months can't take over this way.
- **The moderation window** before sealing, so spam is removed before it's mirrored for good.
- **Prompt injection:** if any client feature ever runs posts through an LLM (summaries,
  moderation help), it must treat every post as hostile input.
- **Scraping can't be prevented:** mirrored public content will be collected, training sets
  included. The client says so where users sign up.

## Leaks and how the design closes them

What each party can learn:

| Observer | Tier 0 and 1 | Tier 2 |
|---|---|---|
| Your ISP | that you use I2P | that you use I2P, plus the clearnet torrents you join |
| The operator | your member key and what you post; not your IP | the same |
| Other peers | an I2P destination that holds certain epochs | your clearnet IP for epochs you fetch |
| Swarm monitors (copyright firms) | nothing | your clearnet IP in that epoch's swarm |

The links between layers, and what closes each one:

1. **The first seeder is the poster.** Closed by having the server and seedboxes seed first
   (see [Posting media](#posting-media)).
2. **A single-file fetch ties an IP to a post.** Closed by fetching whole epochs, after a random
   delay of minutes to hours, never right after a page is viewed.
3. **Timing across layers:** joining a clearnet swarm right after fetching a manifest over I2P
   links the two. Partly closed by that same delay and by fetching in the background on a
   schedule.
4. **File metadata.** Closed by stripping on the client and the server.
5. **Same identity on both layers.** The clearnet BitTorrent client uses a fresh peer ID per
   torrent and never sends the member key or I2P destination.
6. **Copyright notices to tier 2 seeders.** Not technically closable. Seeding on tier 2 is
   opt-in, with a notice, and revoked hashes stop seeding at once.

## Tags (later)

Community tags are signed claims, `{target, tag, author key, time}`, in a format like Nostr's
labelling events (NIP-32). They are published separately from the content and can be ignored.

The client filters by trust, never by raw counts. It shows tags from moderators, from people the
user follows, and from people those vouch for, to a depth the user chooses. Sybil accounts can
add tags, but nobody's filter will count them.

## Off-the-shelf parts

| Need | Candidate | Notes |
|---|---|---|
| I2P router | i2pd, through SAM v3 | emissary (Rust) later, once mature |
| I2P torrents | SAM-capable BitTorrent; I2PSnark's network | Which Rust library supports SAM needs checking |
| Clearnet torrents | a Rust BitTorrent library (librqbit?) | Need to check its BitTorrent v2 and BEP 46 support; per-file SHA-256 means v2 isn't required |
| Signatures | ed25519 (ed25519-dalek) | |
| Serialisation | CBOR, deterministic encoding | |
| Compression | zstd | |
| Image re-encoding | the `image` crate; WebP or AVIF | |
| Video re-encoding | ffmpeg (external) | tier 2 only |
| Perceptual hashing | pHash or PDQ | PDQ is open and built for this |
| Proof of work | SHA-256 puzzles (as in ALTCHA) | |
| Tags | NIP-32 style events | |

Rust throughout, to match rynx and so one client can run on desktops, a Pi and the glasses.

## Node defaults

The server package and the home node both ship with i2pd set up for hosting:

```ini
# i2pd.conf
bandwidth = X     # unlimited class; or a number in KB/s
share = 80        # percent of bandwidth for relaying others' tunnels
[sam]
enabled = true
```

A Raspberry Pi 4 or 5 is enough for a home node: i2pd, the seeding daemon and a few GB of
mirrored epochs.

## Build phases

1. **Text core:** the server accepts signed posts over I2P, seals epochs and publishes a signed
   manifest. A command-line client fetches and verifies the manifest and epochs, and posts.
2. **Mirroring:** sealed epochs shared over I2P torrents; the client fetches from mirrors when
   the server is down; manifests relayed.
3. **Moderation:** moderator certificates, the revocation list, bans, the moderation window.
4. **Tier 1 media:** the upload pipeline, I2P media torrents, the seeding quota and challenges.
5. **Tier 2 media:** seedboxes, clearnet torrents, the delays and notices.
6. **The dedicated client UI**, and read support in rynx.
7. **Tags.**

The Pi can run phases 1 and 2 as a test node from the start.

## Open questions

- **Deletion versus freezing:** is a 72-hour moderation window long enough for small volunteer
  moderator teams? Should it differ per board?
- **Quota size:** what quota stops spam without driving away members who have little
  bandwidth?
- **Operator succession:** if the operator disappears, can the root key hand a site to a
  successor, or does the community fork it under a new root key with the history intact?
- **Readers without keys:** should they mirror too (voluntarily), or would that blur the
  accountability that seeding is meant to buy?
- **Video on tier 1:** never, or short low-resolution clips under a size cap?
- **Server-side search:** on the server only, or a search index shipped with each sealed epoch?
- **Name:** "swarmboard" is a placeholder.
